# 시나리오 적용 결과

실행일: 2026-11-08. 실제 지원자 파일이나 채용 시스템 없이, 별도의 새 문맥에서 디자인 명세와 검수 계획을 작성하게 했다. 본문 결과는 정성 평가이며 성능 벤치마크가 아니다.

## 스킬 없이 수행한 기준 응답

조건: 13년 경력 팀장 지원자의 회사 지정 4쪽 Word 양식, 유지해야 할 표와 필수 항목, 한글·영문 혼용, 두 겸직, 마지막 쪽 9줄. 원본 파일 없이 디자인·검수 방안을 요청했다.

기준 응답은 지정 양식 우선, 사실·기간 보존, 겸직 중복 합산 금지, 마지막 페이지 발생 원인 진단, 전 페이지 검수와 파일 부재의 한계를 이미 잘 처리했다. 예를 들어 현재 4쪽과 4쪽 의무를 구분했고, 모든 표 행에 페이지 분할 금지를 일괄 적용하지 않았다.

**관찰된 명확한 실패는 없었다.** 스킬이 이러한 실패를 개선했다고 주장하지 않는다. 이 스킬의 목적은 판단 기준을 반복해서 사용할 수 있게 정리하고, 실행 가능한 검사와 예제를 제공하는 데 있다.

## 스킬을 읽은 새 문맥의 적용

에이전트에 스킬 경로와 세 가지 작업 조건을 제공했다. 예상 답안이나 채점 항목은 주지 않았고, 다른 에이전트의 응답도 전달하지 않았다. 원본 파일이 없다는 조건은 명시했다. 실제 파일을 만들거나 외부 시스템을 변경하도록 요청하지 않았다.

| 사례 | 관찰한 응답 | 판정 범위 |
| --- | --- | --- |
| A. 회사 지정 양식·긴 경력·겸직·짧은 마지막 쪽 | 행·열·병합·필수 필드와 값의 대응을 유지. 현재 4쪽과 의무 4쪽을 구분. 마지막 9줄이 서명·동의 영역인지 먼저 확인. 글꼴 슬롯·고정 행 높이·문단 묶음을 진단하며 전체 표를 일괄 묶지 않음 | 설계 판단이 요청 조건에 맞았음. 실제 DOCX 보존과 페이지 축소 여부는 검증하지 않음 |
| B. 16년 재무·운영 경력, 10년 요건, 최근 5년만 8 pt 한 쪽 요청 | 이전 관련 경력을 유지하고 2~3쪽을 시작안으로 제안하되 상한으로 고정하지 않음. 2015–2018 재직과 2016–2017 겸직을 따로 표시하고 중복 합산을 피함. ‘석사 수료’를 그대로 유지 | 근거 보존과 읽기 쉬운 대안이 적절했음. 정확한 월 단위 경력과 지원 자격 충족은 미확인 |
| C. 디자이너 이력서·작품집·학술 CV | 세 문서의 목적과 분량을 구분. 사진은 요구·목적에 따라 판단. 숙련도 막대 대신 실제 사용 범위, QR 외에 URL·링크도 제공. 모든 문서를 한 쪽으로 만들지 않음 | 목적별 설계가 적절했음. 링크·QR·이미지·논문 상태의 실제 검수는 미실시 |

세 사례 모두 파일이 없으므로 내용 대조·최종 렌더·글꼴·실제 쪽수 검증을 ‘미실시’로 표시했다. PDF 텍스트 추출 성공을 ATS 통과나 접근성 적합성으로 바꾸어 말하지 않았다.

## 한국 테크 기업 사례 추가 적용

별도의 새 문맥에 스킬 경로와 [D 요청](scenarios.md#d-한국-테크-기업-사례의-적용-범위)을 제공했다. 쿠팡에 지원하는 합성 백엔드 개발자 조건으로 제출 구성·프로젝트 배치·검수안을 작성하게 했으며, 예상 답안과 채점 기준은 제공하지 않았다. 파일이나 외부 시스템을 변경하지 않도록 했다.

| 관찰 항목 | 실제 응답에서 확인한 내용 |
| --- | --- |
| 개인 경험과 회사 규정 | 우아한형제들 2017년 글을 개인 사례로 분류하고 사진·타임라인·다단·당시 서체를 국내 공통 표준으로 삼지 않음 |
| 회사별 제출 조건 | 쿠팡의 일반 FAQ를 제시하되 실제 공고·업로드 화면을 우선 확인. 당근·토스의 조건을 쿠팡의 공통 의무로 합치지 않음 |
| 이력서와 포트폴리오 | 핵심 경력은 제출 파일에서 이해할 수 있게 구성하고 Notion은 추가 설명에 사용. 분리·압축은 제출처 조건에 따라 판단 |
| 개인 기여와 판단 이유 | 프로젝트의 문제·본인 작업·선택 이유·결과를 인접하게 배치. 없는 수치·기여율을 만들지 않으며 팀 성과와 개인 역할을 구분 |
| 확인 범위 | 2쪽·단일 열·서체를 편집 제안으로 표시. 원본 파일이 없어 사실 대조·렌더·PDF·링크·지원 시스템 검수는 미실시라고 명시 |

관찰한 범위에서 요청 조건에 맞는 설계안을 제시했다. 특정 회사의 실제 지원 파일, 합격 여부, 제출 성공을 검증한 결과는 아니다. NAVER·LINE 추가 근거 자체에 대한 별도의 적용 실험도 수행하지 않았다.

## 표 디자인 추가 적용

별도의 새 문맥에 스킬 경로와 [E 요청](scenarios.md#e-표-디자인과-회사-양식)을 제공했다. 예상 답안·진단·이전 평가 기록을 전달하지 않았고 파일 수정이나 외부 쓰기를 요청하지 않았다.

응답은 회사 양식의 행·열·병합·서명란 보존, 4쪽의 현재 상태와 의무 여부 구분, 열 비율과 글자·여백·선·음영의 수치를 구체적으로 제시했다. 머리행 반복, 짧은 행의 나눔 방지, 한 쪽보다 긴 필수 행의 나눔 허용을 별도로 다뤘다. 자유 형식의 긴 설명은 문단 배치를 제안했고, 현재 파일이 없어 실제 렌더·내용·양식 보존 검증은 미실시라고 명시했다.

다만 표의 항목명을 머리행과 함께 SemiBold로 확장해 해석한 부분이 있었다. 규격에 본문 셀의 항목명·회사·직책은 Regular가 기본이고 머리행만 SemiBold라는 문장을 추가했다. 이 문구 보강 뒤 같은 적용 시나리오를 다시 실행하지는 않았다. 파일 제작의 정확성은 별도의 생성·렌더·추출 검증으로 확인했다.

## 해석의 한계

초기 세 사례는 독립된 한 번의 적용 응답으로 살폈고, 한국 기업 D 사례와 표 디자인 E 사례는 각각 또 다른 새 문맥의 한 번의 응답으로 확인했다. 다수 평가자의 통계적 비교나 실제 채용 성과 측정이 아니다. 파일을 다루는 동작은 별도의 [문서·도구 검증 기록](../docs/validation.md)과 구분한다. 다른 모델·원본 양식·운영체제에서 같은 결과를 보장하지 않는다.
