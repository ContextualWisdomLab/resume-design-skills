# 이력서 디자인

지원자의 경력·역할·성과를 쉽게 찾을 수 있게 배치한다. 사실, 제출 조건, 문서의 읽기 순서를 보존하며 서체와 여백을 정리한다. 디자인의 채용 효과나 ATS 통과율은 보장하지 않는다.

## 먼저 정할 것

공고, 원본 파일, 사용자가 명시한 요구에서 아래 정보를 확인한다. 이미 확인한 조건은 다시 묻지 않는다. 미정인 일반 서식은 기본값으로 진행하고, 필수 양식이나 사실의 충돌만 별도로 확인한다.

1. 제출 문서 종류와 대상: 일반 이력서, 상세 경력기술서, 학술 CV, 회사 지정 양식.
2. 제출처의 파일 형식, 용량, 쪽수, 용지, 사진·개인정보 요구.
3. 원본에서 유지할 회사명, 공식 직급, 역할, 기간, 학력, 수치·단위·조건.
4. 편집 범위: 서식만 변경하는지, 내용 편집도 허용하는지.

[디자인 작업표](assets/layout-brief.md)를 내부 작업 기록으로 채운다. 사용자 이력서에 작업표나 조사 메모를 넣지 않는다. 파일이 없으면 디자인 명세를 제공하고 실제 렌더·파일 검증은 미실시로 표시한다.

## 경로 선택

| 조건 | 적용할 경로 | 우선 기준 |
| --- | --- | --- |
| 회사 양식·필수 표가 있음 | [지정 양식 보존](references/employer-forms.md) | 항목·행열·병합·페이지 요구 유지 |
| 자유 형식 일반 이력서 | [기본 프로필](references/design-system.md) | 단일 열, 실제 제목·문단·목록, 직무 관련 경험 |
| 경력이 길거나 팀장급 | 같은 문서의 경력자 프로필 | 책임 범위·기여·결과와 이전 관련 경력의 연결 |
| 학술 CV·상세 경력기술서 | 해당 문서의 제출 규정 | 이력서의 1~2쪽 예시를 상한으로 적용하지 않음 |
| 별도 시각 포트폴리오도 요구됨 | 제출 이력서와 별도 파일로 제작 | 의미 있는 시각 작업만 추가하고 사실 일치 확인 |

직무에 따라 어떤 경험을 강조할지는 내용 작성 스킬에서 정한다. 디자인은 개발·AX·재무·영업·인사·운영 등 직무에 공통으로 적용한다.

## 제작 순서

1. **원본을 보존한다.** 편집용 사본을 만든다. 서식만 고칠 때 핵심 문자열과 본문 순서를 대조 기준으로 남긴다. 숫자·단위·기간·본인 기여를 압축 과정에서 바꾸지 않는다. 겸직은 각각의 기간과 관계를 표시하고 재직 기간을 중복 합산하지 않는다.
2. **정보의 순서를 정한다.** 자유 형식은 이름·연락처, 직무에 맞는 짧은 요약, 경력, 필요한 학력·자격·기술을 기본으로 삼는다. 신입·학술 CV 등은 독자의 판단 순서에 맞춘다. 회사·직책·기간·첫 설명이 함께 읽히게 한다.
3. **한 가지 서체 체계를 적용한다.** [디자인 수치](references/design-system.md)의 기본값에서 시작한다. 한글·영문·숫자를 실제 글꼴로 확인한다. 문자 사이 공백이나 자간 축소로 이름·기술명을 꾸미지 않는다. 글자 크기부터 줄여 페이지 수를 맞추지 않는다.
4. **본문 구조로 조판한다.** Word의 제목 스타일, 문단, 실제 목록을 사용한다. 자유 형식에는 배치용 표, 다단, 떠 있는 텍스트 상자를 기본으로 쓰지 않는다. 연락처는 본문에 둔다. 지정 양식의 표는 유지하고 셀 순서를 따로 검토한다.
5. **페이지 흐름을 조정한다.** 제목과 다음 문단을 연결한다. 긴 경력 전체나 모든 표 행에 묶음 설정을 일괄 적용하지 않는다. 마지막 쪽이 짧으면 나누기·빈 문단·고정 행 높이·문단 간격을 진단한다. 필수 서명·동의 영역은 분량 때문에 없애지 않는다.
6. **제출본을 검증한다.** [검수 절차](references/verification.md)에 따라 최종 수정본의 모든 페이지를 렌더해 보고, 텍스트 추출·핵심 사실·링크·글꼴·양식 보존을 별도로 확인한다. 시각 검수와 구조 검사는 서로를 대체하지 않는다.

## 도구

DOCX 구조와 내용 보존을 검사할 때 실행한다. 경로는 현재 스킬 폴더를 기준으로 해석한다.

```bash
python scripts/audit_docx.py final.docx --baseline original.docx --required-text critical-text.txt
```

`critical-text.txt`에는 반드시 남겨야 할 원문의 문자열을 한 줄에 하나씩 쓴다. `--baseline`은 서식만 수정할 때 사용한다. 내용 편집도 허용된 경우에는 차이를 수동 대조해 승인된 편집과 유실을 구별한다. 검사기는 원본을 수정하지 않으며 ATS, 접근성 적합성, 실제 쪽수·잘림을 판정하지 않는다.

재사용 가능한 합성 예시는 다음 명령으로 만든다. `python-docx`가 필요하다. 예시의 인물·회사·수치는 실제 지원서에 복사하지 않는다.

```bash
python scripts/build_examples.py --output-dir examples
```

렌더러는 사용 환경에서 제공하는 DOCX/PDF 도구를 사용한다. 도구나 글꼴이 없으면 검사한 범위와 남은 확인 사항을 정확히 알린다. 개인 이력서를 외부 ATS 검사 사이트에 자동 업로드하지 않는다.

## 완료 보고

최종 파일과 핵심 변경을 먼저 제시한다. 검증 기록에는 원본·최종 파일, 렌더 도구, 확인한 쪽수, 본문·핵심 사실 대조, PDF 읽기 순서, 글꼴·링크, 접근성·ATS 실측 여부를 각각 적는다. 자동 검사에서 경고가 없다는 사실을 제출 성공으로 표현하지 않는다.

[출처 장부](references/sources.md)의 기관 권고, 제품 문서, 자체 디자인 선택을 구분한다. 지정 양식의 표를 지우기, 긴 경력을 무조건 한 쪽에 넣기, 사진·숙련도 막대를 장식으로 추가하기, 수치를 더 강한 주장으로 바꾸기는 피한다. 공개 예문에는 합성 자료만 사용한다.
