# 이력서 안티패턴과 교정 기준

확인일: 2026-11-08. 대학 커리어센터의 작성 권고, 제품의 파싱 안내, 한국 기업의 제출 조건을 바탕으로 반복되는 문제를 정리한다. 채용 실패율을 실험한 순위나 자동 탈락 규칙으로 사용하지 않는다. 출처 ID는 [출처 장부](sources.md), 기업별 맥락은 [한국 테크 기업 사례](korean-tech-cases.md)를 따른다.

## 검토할 때의 원칙

1. 원본·공고·제출 조건에서 실제 관찰한 문제를 먼저 기록한다. 파일이 없으면 점검 기준을 제시하고 발견·수정·렌더 완료로 보고하지 않는다.
2. 사실 오류·내용 유실·제출 조건 위반, 실제 확인이 필요한 구조 위험, 선택 가능한 시각 개선을 구별한다. 출처의 권고를 기업의 공식 탈락 규칙으로 바꾸지 않는다.
3. 내용 수정 권한을 확인한다. 서식만 바꾸는 작업에서는 성과·직책·기간·학력 문구를 임의로 보강하지 않는다. 내용의 선택·새 서술은 해당 이력서·경력기술서 작성 스킬과 연결한다.
4. 공고의 필수 양식·사진·서명·개인정보 항목을 일반 조언만으로 삭제하지 않는다. 실제로 불필요한 정보와 제출처가 요구한 정보를 구분한다.
5. D1·D2는 기존 디자인 기본값이고, 아래 D3는 이 프로젝트의 교정·검증 판단이다. 제품별 위험과 편집 판단에 다른 표지를 붙여 보고한다.

## 한국 테크 기업에 적용할 때

| 자료의 성격 | 반영할 판단 | 확대하면 안 되는 해석 |
| --- | --- | --- |
| 토스 일반 합류 안내 K3 | 경험의 영향·학습, 필요한 기술 정보가 찾아지게 배치 | 특정 서체·표 구성이나 모든 직무의 동일 템플릿 의무 |
| 당근 디자인 공고 K5 | 공동 작업에서 본인의 역할·기여를 확인할 수 있게 구성 | 모든 직무에 숫자형 기여율 제출을 강제 |
| LINE의 2019년 개인 경험 K7 | 무엇을·어떻게·왜 했는지 연결 | 당시 작성자의 선택을 현재 전사 채용 규칙으로 선언 |
| 우아한형제들 블로그의 2023년 신입 경험 K9 | 설명 가능한 기술·본인 역할·작동하는 링크를 점검 | 프로젝트를 한 개만 남기거나 글의 불합격률 표현을 검증된 통계로 사용 |
| 쿠팡 K1과 당근 K4의 FAQ | ZIP·링크 등 서로 다른 제출 조건을 회사별로 확인 | 어느 한쪽의 조건을 한국 테크 기업 공통 규칙으로 채택 |

기업 문서의 긍정적 작성 조언에서 도출한 안티패턴은 이 스킬의 편집적 적용이다. 원문이 해당 패턴을 불합격 사유라고 직접 선언했다고 표현하지 않는다. 현재 공고·직무 안내가 과거 사례보다 우선한다.

토스는 개발 직군의 기술 스택 기재를 요청한다(K3). 따라서 ‘기술 목록은 전부 삭제하라’고 교정하지 않는다. 목록을 유지하고 실제 경험과 연결하는 것, 설명할 수 없는 기술을 확인 없이 전문 역량으로 주장하지 않는 것을 구별한다.

## 단정하면 안 되는 통념

| 통념 | 이 스킬의 판단 |
| --- | --- |
| ‘표·다단이 있으면 ATS에서 무조건 탈락한다’ | Greenhouse의 실패·부분 실패 위험은 제품 안내다. W3C에는 올바른 읽기 순서를 갖춘 다단 예시도 있다. 파싱과 채용 결정을 구별한다(S3, S6). |
| ‘PDF로 저장하면 안전하다’ | 파일 형식, 실제 텍스트, 시각 배치, 읽기 순서, 제출처 지원은 서로 다른 확인이다(S5, S6). |
| ‘경력자는 무조건 한 쪽 또는 두 쪽이어야 한다’ | 대상 독자·문서 종류·공고 조건을 따른다. 교육기관의 특정 대상 조언을 모든 경력기술서에 강제하지 않는다(D1). |
| ‘모든 성과에는 숫자가 있어야 한다’ | 수치가 있으면 조건과 함께 쓰되, 없으면 확인된 역할·산출물·결과를 구체화한다. 임의 숫자는 추가하지 않는다(S15). |
| ‘ATS 90점이면 합격 확률이 90%다’ | 점수와 실제 파싱·채용 결과를 연결하는 검증 근거가 없다면 그런 확률을 말하지 않는다(D3). |
| ‘사진과 개인정보는 항상 삭제해야 한다’ | 국가·직무·회사 양식의 요구를 확인한다. 불필요한 노출을 줄이는 판단과 필수 항목 삭제를 구별한다(S1, D3). |
| ‘6초 또는 7초 안에 읽히는 템플릿이 합격을 보장한다’ | 이 프로젝트는 고정 심사 시간이나 특정 배치의 채용 효과를 검증하지 않았다(D3). |

## 사실을 보존하는 합성 교정 예시

아래는 연구용 합성 자료다. 실제 지원자의 성과로 복사하지 않는다.

### 업무 나열을 문제와 기여로 연결

검토 전: ‘Python 자동화, 운영 프로세스 개선, 생산성 혁신.’

제공된 사실: 주간 집계에서 같은 요청을 중복 집계하는 문제가 있었다. 본인은 요청 ID 중복 검증 스크립트와 확인 절차를 만들었다. 담당 팀은 6명이었다. 시간 절감량이나 도입 후 오류율은 측정하지 않았다.

교정안: ‘6명 운영팀의 주간 집계에서 요청이 중복 집계되는 문제를 다뤘다. 요청 ID를 대조하는 Python 검증 스크립트와 확인 절차를 작성했다.’

왜 개선되는가: 문제·대상·본인 행동을 설명하고 미측정 성과를 만들지 않는다. 도입 범위와 결과가 추가로 확인되면 연결한다. ‘오류 0건’이나 ‘생산성 50% 향상’으로 마무리하지 않는다.

### 팀 성과와 개인 기여를 구분

검토 전: ‘프로세스를 혁신해 처리율 15% 향상.’

제공된 사실: 같은 정의로 집계한 팀의 기한 내 처리율은 개선 전후 각 4주 동안 75%에서 90%로 바뀌었다. 본인은 분류 기준과 예외 처리 안내를 작성했다. 다른 팀원들은 도구 설정과 교육을 담당했다. 개인별 효과는 분리 측정하지 않았다.

교정안: ‘팀의 기한 내 처리율이 전후 각 4주 기준 75%에서 90%로 높아진 개선 과제에 참여했다. 본인은 분류 기준과 예외 처리 안내를 작성했다.’

왜 개선되는가: 팀 결과와 본인 행동을 구분한다. 변화량을 덧붙일 필요가 있다면 15%p 또는 기준값 대비 20% 증가로 정확히 구분한다. 개인 기여율이나 단독 인과 효과를 추정하지 않는다.

## 결과 기록

발견 사항마다 **원본 위치 → 관찰한 상태 → 영향과 근거 범위 → 교정안 → 확인 방법·결과**를 기록한다. ‘보기 싫다’는 취향만으로 오류를 선언하지 않는다. 실제 발생한 유실·잘림과 아직 확인하지 않은 파싱 위험을 구별한다.

공고에 없는 요구, 원자료에 없는 성과, 원본을 보지 않은 사실 대조, 실행하지 않은 렌더·ATS 결과를 추가하지 않는다. 미확인 사실이 있어도 확인된 내용의 디자인·정리는 진행하고 필요한 확인 항목을 따로 남긴다. [제출본 검수](verification.md)로 수정 결과를 확인한다.
