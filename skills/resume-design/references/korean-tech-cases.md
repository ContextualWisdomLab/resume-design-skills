## 적용 순서

1. 해당 지원 건의 현행 공고, 제출 화면, 채용 담당자의 명시적 안내를 확인한다.
2. 그다음 공식 일반 안내와 해당 직무의 작성 가이드를 참고한다. 날짜·직무·지역·법인이 다른 자료를 공통 의무로 만들지 않는다.
3. 직원의 개인 사례는 참고한 구성과 확인한 한계를 함께 적는다. 개인의 합격 경험을 디자인의 채용 효과로 해석하지 않는다.
4. 실제 파일이 없으면 구성안만 제시하고 렌더·글꼴·쪽수·제출 검증은 미실시로 남긴다.

## 기업별 근거와 디자인 적용

### K1. 쿠팡 — 제출 파일과 링크 조건

출처: [Coupang Careers 한국어 FAQ](https://www.coupang.jobs/kr/how-we-hire/faq/). 게시·갱신일 미표시. 확인 범위는 서류 전형의 양식·파일 안내다.

- **직접 확인:** 자유 양식, PDF·Word 권장, 여러 파일은 ZIP 제출 안내, 문서 내 URL을 가급적 피하라는 권고, 파일당 100 MB 이하.
- **디자인 적용:** 주요 경력·성과를 파일 자체에서 이해할 수 있게 쓴다. 포트폴리오를 링크로만 전달하지 않고 해당 지원 화면에 맞춰 첨부 조합을 정한다. 압축을 요구받으면 내부 파일명과 열림도 확인한다.
- **범위:** FAQ의 권장과 제한을 구분한다. 별도 자회사·직무 안내까지 동일하다고 단정하지 않으며, 실제 제출 전에 다시 확인한다.

### K2. 우아한형제들 — 직원의 실제 제작 사례

출처: 구인본, [이직초보 어느 개발자의 이력서 만들기](https://techblog.woowahan.com/2531/), 2017-07-17. 공식 기술블로그에 실린 개인 경험이며 현행 채용 정책은 아니다. 본문과 첫 페이지·경력 페이지 이미지 두 장을 확인했다.

- **직접 확인:** 첫 장의 짧은 소개, 최근 프로젝트부터 이어지는 순서, 문제해결 사례, 일관된 여백과 절제된 강조를 설명한다. 공개 이미지에는 사진·기술 타임라인과 왼쪽 제목/오른쪽 본문 구성이 있다.
- **디자인 적용:** 관련 경력과 문제해결의 맥락을 앞에 두고 제목·역할·기간을 반복 가능한 단위로 묶는다. 실제 이미지는 정보 배치의 비교 대상으로만 참고한다.
- **범위:** 사진·아이콘·다단·여러 쪽 구성을 공통 권장으로 복제하지 않는다. Apple SD Gothic·KoPub 등 당시 글꼴 추천도 작성자 의견이다. 원문 이력서 이미지와 개인 정보는 패키지에 재배포하지 않는다.

### K3. 토스 — 영향·학습과 PDF 변환

출처: 토스 채용팀, [Joining the Toss Community](https://toss.im/career/joining-guide)의 지원 안내. 게시·갱신일 미표시. 이번 열람에서는 영문 본문을 확인했다.

- **직접 확인:** 자유 형식, 경험의 영향과 배운 점 중심 작성, 개발 직군의 기술 스택 기재, 개별 공고의 작성 권고 확인을 안내한다. HWP·Word 문서는 글꼴·서식 오류를 피하도록 PDF로 변환하라고 안내한다. 주민등록번호·자택 주소·현재 연봉은 필요하지 않다고 명시한다.
- **디자인 적용:** 업무 목록 뒤에 결과를 묻어 두지 않고 경험별 영향·학습을 가까이 배치한다. 기술 스택은 읽을 수 있는 텍스트로 표시하며 PDF 변환 후 서체와 줄바꿈을 검수한다.
- **범위:** 특정 글꼴·쪽수·단 구성을 지정한 근거는 아니다. 공고별 안내와 지원 화면을 우선하며, 온라인 작성 기능을 제공하는 지원 건까지 첨부 파일 필수라고 단정하지 않는다.

### K4. 당근 — 자유 형식과 제출 방식

출처: [당근 채용 FAQ — 지원 관련](https://careers.daangn.com/faq/지원-관련/). 게시·갱신일 미표시.

- **직접 확인:** 자유 형식과 PDF를 권장하며 HWP·Word는 호환 문제로 지양하도록 한다. ZIP은 제출할 수 없고, 웹 링크는 이력서·포트폴리오 파일 안에 첨부하도록 안내한다. 국내 포지션은 국문을 권장한다.
- **디자인 적용:** 문서 안에서 링크의 목적을 알 수 있게 표시하고 내보낸 PDF에서 클릭 대상을 확인한다. ZIP을 기본 납품·제출 형식으로 정하지 않는다.
- **범위:** 쿠팡(K1)의 압축·URL 안내와 다르다. 회사별 결과물을 분리하고 실제 첨부 수·용량은 해당 지원 화면에서 확인한다.

### K5. 당근 디자인 직무 — 협업 기여의 가시성

출처: [Brand Designer (계약직) — 브랜딩 (서비스 브랜딩 & UI)](https://careers.daangn.com/jobs/role/6589282003/). 게시·갱신일 미표시. 해당 직무 공고의 자격요건·제출 안내를 확인했다.

- **직접 확인:** PDF 포트폴리오가 필수이며 협업 프로젝트의 기여도와 역할을 표시하도록 요구한다. 타이포그래피·편집디자인 역량을 자격요건으로 제시한다.
- **디자인 적용:** 결과물 가까이에 본인 역할·담당 범위를 배치한다. 기여도를 임의의 퍼센트로 만들지 않고 확인된 업무로 설명한다. 작품의 화면·설명·기여가 서로 떨어지지 않게 한다.
- **범위:** 이 역할의 요구를 모든 직무에 확대하지 않는다. 본문 일부에 ‘인턴’ 표현이 섞여 있어 그 문장의 허용 범위는 채택하지 않았다. 특정 서체나 그리드의 지정 근거도 아니다.

### K6. LINE — 간단한 이력서와 상세 포트폴리오

출처: 배지훈·이진아·문범우, [2020 상반기 LINE 신입 개발자 3인의 WOW한 입사기!](https://engineering.linecorp.com/ko/blog/2020-first-half-new-liners-interview/), 2020-09-03. 당시 LINE+·LINE BIZ+ 서버 개발자의 개인 경험이다.

- **직접 확인:** 한 입사자는 프로젝트 구조·자신의 역할·사용 기술·Git 주소를 포트폴리오에 담았고, 다른 입사자는 이력서는 짧게 쓰고 포트폴리오에서 자세히 설명했다고 말한다.
- **디자인 적용:** 요약에서 대표 경험을 찾고 상세 자료에서 구조와 구현 근거를 확인하도록 연결한다. 같은 프로젝트의 역할·기술·증거를 가까이 둔다.
- **범위:** 당시 신입 사례이며 현재 LINE의 필수 항목·링크 정책·쪽수 규칙이 아니다. Git 링크를 모든 회사의 제출본에 강제로 추가하지 않는다.

### K7. LINE — 무엇을, 어떻게, 왜 했는가

출처: 김준호, [LINE 서버 개발자가 되기까지 내가 준비한 것들](https://engineering.linecorp.com/ko/blog/things-i-prepared-to-be-a-line-server-developer/), 2019-10-21. 개인의 이직 준비 경험이며 마이크로소프트웨어 397호 기고문임을 표시한다.

- **직접 확인:** 이력서의 짧은 업무 설명을 포트폴리오에서 구체화하고 수행 내용·방법·이유를 보여 주도록 조언한다. 지원 직무의 요건과 업무에 맞춰 자료를 구성한다.
- **디자인 적용:** 결과 옆에 문제와 선택 이유를 함께 놓고, 관련성이 높은 사례에 충분한 지면을 배정한다. 화면·구조도만 제시하지 않고 본인 판단을 설명할 문장을 확보한다.
- **범위:** 오래된 프로젝트를 피하라는 저자의 조언을 일률적인 경력 삭제 규칙으로 쓰지 않는다. 관련 실무 연수를 보여 주는 초기 경력도 보존한다.

### K8. NAVER — 온라인 제출과 완료 확인

출처: [NAVER Careers 한국어 FAQ](https://recruit.navercorp.com/bbs/faq.do?lang=ko). FAQ 게시·갱신일 미표시. 상단의 2026-04-10은 별도 사칭 주의 공지의 날짜다.

- **직접 확인:** 채용 홈페이지에서 온라인 지원을 받으며 완료 화면·안내 메일·마이페이지로 접수를 확인할 수 있다. 홈페이지 수정·삭제는 공고 마감과 서류 검토 전까지 가능하다고 안내한다.
- **디자인 적용:** 첨부 문서 외에 온라인 입력 항목과 내용이 맞는지 확인하고, 제출이 별도로 허가된 작업에서는 접수 완료 근거도 확인한다.
- **범위:** 제출 절차의 근거다. PDF·글꼴·쪽수·이력서 항목 순서를 지정하는 자료로 사용하지 않는다. NAVER의 다른 법인·개별 공고까지 같은 조건이라고 추정하지 않는다.

### K9. 우아한형제들 — 신입 개발자의 이력서 수정 경험

출처: 권시연, [왕초보 신입 개발자의 우당탕탕 이력서 작성기](https://techblog.woowahan.com/11998/), 2023-05-23. 글에서 회사의 공식 의견이 아닌 개인 경험이라고 명시한다.

설명하지 못하는 기술까지 채우기, 구현한 기능만 적기, 원하는 페이지로 바로 열리지 않는 링크를 돌아보며 수정한 사례다. 실제 경험과 역할을 구체화하고 링크를 확인하는 판단에 참고한다. 이를 현행 채용 정책으로 표현하거나 저자의 프로젝트 개수·배치를 공통 규칙으로 만들지 않는다. 글의 불합격률 표현도 통계적 근거로 채택하지 않는다.

[안티패턴 교정](anti-patterns.md)의 AP02·AP18과 함께 읽는다. 저자의 실제 이력서·사진·수치를 예제에 복제하지 않는다.

## 자체 적용안: 판단 근거가 함께 읽히는 경력 단위

아래는 기업 지정 양식이 아닌 이 스킬의 정보 배치 제안이다. 사실 선택·검증은 내용 작성 스킬에서 처리하고, 디자인 단계는 확인된 내용의 관계를 보존한다.

| 읽는 순서 | 같은 묶음에 둘 정보 | 배치 이유 |
| --- | --- | --- |
| 식별 | 회사·팀·역할·기간 | 어느 경력과 기간에 속한 일인지 즉시 연결 |
| 맥락 | 해결할 문제·고객 또는 사용자·제약 | 성과 수치가 필요한 이유와 적용 범위 전달 |
| 판단과 기여 | 선택한 접근과 이유·본인이 맡은 일 | 기술명·팀 성과만으로 개인 역량을 추측하게 하지 않음 |
| 결과 | 확인한 변화·측정 조건·남은 한계 | 숫자와 대상·기간·조건을 함께 해석 |

이 네 묶음은 문단이나 짧은 글머리표로 표현한다. 매 프로젝트에 고정 소제목 네 개를 강제하거나 각 수치를 큰 카드로 분리하지 않는다. 자료가 부족하면 추가 확인 대상으로 남기며 선택 이유·기여율·지표를 창작하지 않는다. 서식만 바꾸는 요청에는 원문을 재서술하지 않고 배치만 조정한다.

이력서는 경력과 판단 근거의 요약, 포트폴리오는 작업 과정·결과물을 검토할 수 있는 상세 자료로 구성한다. 두 목적을 구분하되, 물리적 파일을 하나로 합칠지 여러 개로 낼지는 해당 채용처가 정한다.

## 회사별 제출표

`assets/layout-brief.md`에 회사·직무별로 아래를 기록한다. 하나의 공통 제출본을 모든 기업에 그대로 보내지 않는다.

| 기록 | 확인할 사항 |
| --- | --- |
| 근거 | 공식 URL·확인일·작성 또는 갱신일·해당 직무 |
| 강도 | 필수·권장·작성자 의견의 구분 |
| 파일 | PDF·Word·웹 링크 허용, 크기·첨부 수·병합·압축 조건 |
| 내용 | 이력서·경력기술서·작품집의 역할, 필수 질문·개인정보 항목 |
| 검수 | 최종 모든 쪽, 텍스트·기간·수치, 글꼴, 허용된 링크·열람 권한 |

공고와 FAQ가 충돌하면 해당 지원 건의 더 구체적인 최신 안내를 확인한다. 어느 쪽이 최신인지 불명확한 필수 조건은 추정하지 않는다. 읽기 전용 조사만으로 실제 업로드·ATS 입력·채용 적합성을 검증했다고 보고하지 않는다.

## 서체와 예제의 범위

Pretendard Regular 본문·SemiBold 소제목·Bold 이름, 본문 11 pt, 단일 열의 기본값은 이 프로젝트의 선택이다. 위 회사가 Pretendard나 동일한 쪽수를 권장한다는 뜻이 아니다. 기업 브랜드 글꼴과 지원서 서체 요구도 서로 구분한다. 공개 DOCX·PDF는 합성 예제이며 특정 기업의 공식 템플릿 또는 합격 이력서로 소개하지 않는다.

이번 목록은 확인한 자료를 선별한 것이다. 카카오 후보 글은 본문을 확보하지 못해 채택하지 않았고, 열기에서 404가 난 당근의 과거 공고도 제외했다. 관련 안내가 없다는 뜻은 아니다. 제출 규칙은 지원할 시점에 해당 공고와 공식 화면에서 다시 확인한다.
