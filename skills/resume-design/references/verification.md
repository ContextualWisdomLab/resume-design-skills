# 제출본 검수

## 서로 다른 네 가지 확인

| 확인 | 방법 | 증명하지 못하는 것 |
| --- | --- | --- |
| 사실·내용 보존 | 원문과 회사·직책·기간·수치·단위·기여·조건 대조 | 실제 글자 잘림 |
| DOCX 구조 | XML·스타일·표·변경 추적·주석·숨김 점검 | 최종 PDF의 순서·폰트 |
| 실제 외관 | 최종 수정 후 모든 쪽을 렌더하여 보기 | 스크린리더·실제 ATS 결과 |
| 제출 환경 | 업로드 미리보기와 자동 입력 필드 대조 | 채용 결정·모든 ATS 호환성 |

S3와 S5의 제품 안내는 특정 파서의 범위다. 한 제품의 입력 지원이나 지역 텍스트 추출 결과를 모든 채용 시스템에 일반화하지 않는다.

## 1 내용과 구조

[안티패턴 목록](anti-patterns.md)을 실제 원본에 적용한다. 사실·단위·기여 오류나 유실과 조건부 파싱 위험을 구별하고, 글꼴·표·분량의 취향을 자동 탈락 기준으로 사용하지 않는다. 파일이 없으면 발견·수정 완료가 아닌 점검 기준으로 보고한다.

서식만 바꾸는 작업이면 원본을 보존하고 다음을 실행한다.

```bash
python scripts/audit_docx.py final.docx --baseline original.docx --required-text critical-text.txt
```

필수 문자열은 원문에서 가져오고 UTF-8 파일의 각 줄에 하나씩 적는다. 회사명, 직책, 자격 상태, 중요한 수치와 조건을 넣는다. 사용자 데이터가 포함된 검사 파일·로그는 공개 예제나 저장소에 올리지 않는다.

종료 코드 0은 자동으로 찾은 차단 항목이 없다는 뜻이다. 1은 내용 차이·누락·검토 흔적 등 수동 해결이 필요한 항목, 2는 잘못된 입력이나 읽기 실패다. 표·머리말·그림 등의 경고는 지정 양식 또는 페이지 번호일 수 있다. 경고를 없애려고 필수 구조를 삭제하지 않는다.

검사기는 공백을 정규화한 XML 본문 순서와 문자열을 비교한다. 제목 스타일의 상속, 글자 크기·색의 최종 계산, 페이지 수, PDF 태그, 표 셀 관계, 렌더 잘림은 검사하지 않는다. 변경 추적과 주석은 렌더에서 보이지 않을 수 있으므로 구조에서도 확인한다. 승인된 수정인지 확인한 뒤 제출본의 검토 흔적을 정리한다.

## 2 모든 페이지의 렌더

환경의 DOCX 렌더러나 Word/LibreOffice PDF 내보내기로 최종 파일을 렌더한다. 해당 환경의 문서·PDF 스킬이 있으면 따른다. Poppler가 있으면 PDF 페이지를 이미지로 확인할 수 있다.

```bash
mkdir -p review
pdftoppm -png -r 120 final.pdf review/page
pdfinfo final.pdf
pdffonts final.pdf
pdftotext -layout final.pdf extracted-layout.txt
pdftotext final.pdf extracted-flow.txt
```

두 텍스트 추출 모드를 함께 보아도 읽기 순서·접근성을 완전히 증명하지는 못한다.

모든 페이지를 읽을 수 있는 크기로 열고 제목 고립, 글자·표 잘림, 빈 쪽, 들쭉날쭉한 간격, 불필요한 마지막 쪽, 줄에 홀로 남은 날짜를 확인한다. 한글·영문·숫자·기호를 실제로 읽는다. 렌더 후 글꼴·간격·내용을 수정했으면 다시 렌더한다.

표는 [표 전용 검수](table-design.md#제작과-검수)를 추가한다. 열 폭·셀 여백·테두리·음영·숫자 정렬과 반복 머리행을 확인하고, 짧은 행과 한 쪽보다 긴 필수 행의 나눔을 구분한다. 원본과 표·행열·병합·항목값 대응을 대조한다. `audit_docx.py`의 표 개수·고정 행 높이 경고만으로 이 검수를 대신하지 않는다.

## 3 텍스트·글꼴·링크·접근성

- 추출 텍스트에서 이름·연락처와 경력 순서를 확인한다. 회사·직책·기간·성과가 다른 행이나 셀과 섞이지 않아야 한다.
- 글꼴 포함 여부와 한글 검색·복사 결과를 확인한다. 글꼴이 포함돼 있어도 글자 매핑이나 실제 모양이 맞는지 확인한다.
- 제출처의 링크 허용 여부를 먼저 확인하고, 포함한 하이퍼링크의 표시값과 실제 대상이 같은 사람·포트폴리오를 가리키는지 확인한다. 파일 제출 요구를 웹 링크로 대체하거나 QR코드만으로 연락처를 제공하지 않는다.
- Word의 제목·목록 구조와 접근성 검사 결과를 확인한다(S4). PDF 태그·논리 순서·스크린리더 확인은 별도 단계로 기록한다. 태그가 있다는 사실만으로 접근성 적합성을 선언하지 않는다(S6).
- 본문에서 필요한 개인정보와 파일 속성·주석의 불필요한 메타데이터를 구별한다. 사용자 확인 없이 필수 연락처를 삭제하지 않는다.

## 4 파일 선택과 완료 보고

공고가 지정한 형식을 우선한다. PDF는 시각 배치를 고정하는 데 유용하고 DOCX는 편집 가능한 원본을 제공하지만 어느 형식도 보편적인 ATS 합격을 보장하지 않는다. 두 형식이 요구되면 최종 내용이 같아야 한다.

실제 지원 시스템의 미리보기·필드 결과를 확인할 수 있고 사용자가 그 작업을 요청했다면 확인한다. 일반 디자인 작업만으로 제3자 사이트에 이력서를 전송하거나 지원서를 제출하지 않는다.

완료 보고에는 다음을 남긴다.

| 항목 | 허용되는 보고 |
| --- | --- |
| 파일·쪽수 | 실제 최종 파일과 렌더에서 확인한 쪽수 |
| 외관 | 모든 쪽 확인 / 일부 확인 / 렌더 미실시 |
| 사실·순서 | 원본 대조 범위, 변경 사유, 남은 충돌 |
| 글꼴·링크 | 실제 확인 결과 또는 미실시 |
| 접근성 | 구조 검사·태그·스크린리더 각각의 수행 여부 |
| ATS | 실제 제품과 입력 결과 또는 미실시 |

원본이 없거나 렌더가 실패했으면 명세 또는 검토본으로 전달한다. 검사하지 않은 파일을 제출 준비 완료로 표현하지 않는다.
